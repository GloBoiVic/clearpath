# Architecture

## V1 architecture (decided 2026-11-21)

Product rules are in `docs/BRIEF.md` → V1. The diagram is `docs/architecture/clearpath-v1.excalidraw`.

**Victor's decision, 2026-11-21: no paid Apple Developer Program for now.** Apple only allows the DNS proxy system extension to paid members, so V1 does not use it. V1 uses the option the 2026-11-17 assessment below set aside, a local DNS service, and accepts its costs. The extension stays the upgrade path.

Components:

- **Filter service.** A Swift background system service (a LaunchDaemon that launchd restarts on exit) runs the `clearpath-filter` loopback listener and drops to `nobody` after binding. The installed network services point their DNS at it. The filter reuses the policy and DNS code from `native-dns-foundation` and selects the upstream from the live System Configuration store for each forwarded lookup. TCP retries keep that route. A supplemental suffix takes priority, with the most specific match first. Ordinary lookups use the active network service's saved manual DNS or its current negotiated servers. An unusable matching scope fails rather than falling back to the ordinary resolver. Upstreams use IP literals and exclude the loopback listener. macOS continues to apply its search domains and handle Bonjour. VPNs and applications that send DNS outside the loopback listener can still bypass local filtering. Detecting a DNS setting or policy changed outside Clearpath is tracked in #21.
- **Service control.** `clearpath-service` installs, removes and reports the filter service: LaunchDaemon `io.clearpath.filter`, files in `/Library/Application Support/Clearpath`, and a recovery record of every network service's original DNS written before any change. The filter binds port 53 as root, then runs as `nobody`. Uninstall restores DNS before it stops the daemon.
- **Menu-bar app.** A Swift menu-bar app with no Dock icon: setup, status, block a site, request a removal, partner settings, uninstall. It controls the filter service locally. Quitting it does not stop filtering.
- **Browser profile.** `clearpath-service browser-profile` generates a removable system profile using macOS managed preferences. The setup window reveals the bundled profile for manual installation in Device Management. It turns off browser-managed DNS-over-HTTPS in Chrome, Brave and Firefox. Site blocking and the configured Google, Bing and DuckDuckGo SafeSearch mappings use the DNS filter. Chrome also forces Google SafeSearch on Google hostnames outside the DNS list (Victor, 2026-11-22). Brave gets the same `com.brave.Browser` settings as Chrome (`DnsOverHttpsMode` off, `ForceGoogleSafeSearch` true), because Brave's own secure DNS bypassed Clearpath until locked (#69), plus `TorDisabled` so Brave's "New Private Window with Tor" is unavailable; regular Brave private windows stay (Victor, 2026-11-26). For Safari it forces only `EnableEnhancedPrivacyInPrivateBrowsing` to false in `com.apple.Safari`, Safari's undocumented key for "Use advanced tracking and fingerprinting protection" in Private Browsing. While that protection is on, Safari private windows bypass the system DNS path, and so do normal windows when it is set to all browsing (#61). Victor chose "Build private-only lock" on 2026-11-26: the regular-browsing key stays unmanaged. Safari then dims the whole setting and treats it as off in every window, while Prevent cross-site tracking stays on. Turning off Safari Private Browsing itself isn't possible here: both of Apple's keys for it (`AllowPrivateBrowsing`, `allowSafariPrivateBrowsing`) require an MDM server.
- **Partner service.** A small open-source, self-hostable web service intended for a free tier. It stores partner emails, the pairing, check-ins, status events and approval requests, sends email, and serves a confirmation page for Approve and Deny. It never receives browsing data. It raises the 24-hour "hasn't checked in" alert and applies the 7-day no-answer rule. The pairing service uses a synthetic local mail sink until hosted deployment.
- **Python DNS** stays as the test harness and reference implementation. The Mac's filter uses Swift. The pairing service uses Python and SQLite.

Fail closed: if the filter service is down, lookups fail until launchd restarts it. If it stays down, the menu-bar app offers "Restore internet", which restores the previous DNS setting and alerts the partner.

The panel polls the service tool for the daemon PID, a nameless loopback DNS response and the configured and effective default DNS paths. An inconclusive check shows an unknown state. For recovery, the installer places a root-controlled copy of `clearpath-service` with the filter. The app requests macOS administrator approval for that copy's fixed `restore` command. The command checks again for a restart and writes a durable recovery marker before changing DNS. It reuses the original DNS record and verifies the restored settings. A retry resumes the same recovery and preserves the event ID. `status` exposes the completed event ID and timestamp for #20 to deliver. Uninstall removes the local event along with the other service files.

The menu-bar app reads installed block rules through `clearpath-service blocked-sites`. The system XPC service lets the current console user add a custom domain. The service uses the shared domain validator and serializes the read, validation and atomic replacement with install, restore and uninstall. It preserves the other rules and leaves repeat additions unchanged. The filter checks the policy file for changes and swaps in a complete, valid policy for new queries. Malformed or unreadable changes leave the last valid policy active.

### Site removal requests

The current console user can request removal of a selected custom block or adult list rule through the system XPC service. The service records a unique request ID, normalized domain and rule type under the installed service lock. The app lists pending and recent completed requests. It can submit requests and read status. The privileged service obtains outcomes itself from the installer-configured pairing origin over HTTPS, using the pairing's owner credential from a root-only file. It verifies the response ID and domain before applying it. The loopback pairing demo runs under the app user and is used for synthetic proof. The installed service requires its own trusted HTTPS pairing origin.

The pairing service receives the request ID and domain. It captures the accepted partners at submission and publishes a single private mail batch with a distinct token for each recipient. The decision record stores token hashes. The private outbox holds message contents until the sink publishes them. An email link opens a page that verifies the token and shows the site. Only an explicit Approve or Deny can decide the request. A SQLite transaction resolves the first valid decision and invalidates both tokens. A repeat submission with the same ID and domain returns its existing state.

The deadline is seven elapsed days from publishing the request batch, or from submission if there are no accepted partners. The pairing host owns the clock. Its elapsed clock covers service restarts within the same host boot when the OS provides a boot identifier. A reboot uses the pairing host's trusted UTC to count downtime. On a partner install the site's Mac clock has no role. The server persists the terminal outcome and queues a deadline notice to the original recipients. If the installed service is offline, it catches up on return.

A solo install has no pairing service to own the clock. The recovery record notes whether install wrote a pairing configuration. An install is solo only while that record says no, no partner pairing has been reported, and neither a pairing configuration nor an uninstall event exists. On a solo install, the service gives each new request a deadline seven days after submission on this Mac's clock and lists it with that deadline. The site-block daemon runs at boot and stays running for every install. Every few seconds it marks a solo request past its deadline as `timed_out` and applies it through the same journal. Any other state keeps the block: a record from before this field, a partner install missing its configuration, or a request without a deadline on a solo install.

Solo removals count seven days on the Mac's clock, a known limit Victor accepted on 2026-11-26. An administrator who sets the clock forward can shorten the wait. On a solo install that is no weaker than uninstalling, which the same administrator can do at once. Partner installs never use the Mac's clock.

A partner can also be set up after a solo install, through Partner settings with a pairing service. When the app runs with a partner service, it tells the installed service through `clearpath-service record-partner-pairing`. It does this at launch, before reading requests, and before each Partner settings action. The service writes the root-owned `partner-pairing.json` marker. Only uninstall removes it, so from then on the install is never solo. In the same locked step, the service marks each open solo request `cancelled`, and the daemon does the same if it finds the marker beside an open solo request. New requests take the partner path, which refuses them until the service has its own pairing configuration, so the block stays. A writer that chose a solo deadline before the marker appeared is refused under the service lock. The request list stays readable in every installed state, so a cancelled request remains visible.

The installed service journals the confirmed authorization before editing policy. Reconciliation can then retry a validated atomic write and keep the other rules intact. Custom removal deletes the matching custom entry. Adult list removal adds an exception for the selected domain and its subdomains, and later source refreshes preserve it. An independent custom or parent rule may still cover the name. Re-adding a custom block retires any in-flight authorization for the removed instance before writing the new rule.

### Setup and partner changes

The pairing service records setup completion once, in its own table, with whether the user finished alone. Finishing alone is accepted only when no partner is invited or accepted, and finishing with a partner only when one is. Removals already go through the decision flow, so the lock applies from the first moment. Invitations the user sends stay freely correctable until accepted.

Replacing an accepted partner is a request of kind `partner-change` in the same `requests` table, with its role, revision and both addresses in `partner_changes`. It goes to every accepted partner, which means the one being replaced and the other partner if there is one, under the same tokens, first-response rule and seven-day deadline. One change can be open at a time. An invitation that an approved change created is marked `approved`: it can be sent again to the same address, but only another partner change can redirect it, decided by the accepted partners, or after seven days when there are none. Approval or the deadline applies a change in the deciding transaction: the slot gets the new address as a fresh, `approved` pending invitation, and the replaced partner's links and queued request mail for every open request are withdrawn. A request left without a queued link starts its seven days then. The outbox publishes the new invitation and the notice to the replaced partner, plus a notice to the other partner after a timeout, as one `<id>-applied` batch. Requests saved before this change are migrated as site removals.

### Missed check-ins

The installed `io.clearpath.site-blocks` daemon checks in on startup and hourly, including after an overdue wait during sleep. It uses the same root-only pairing configuration and HTTPS connection as site removals. The daemon reads an opaque revision and sends it back in an authenticated POST. The service atomically rotates it and stores its receipt time. A replay leaves the receipt time unchanged. The requests contain no device details, protection checks, blocked attempts or browsing data.

The pairing host uses the same clock as approval deadlines. Monitoring starts once the Mac has checked in and at least one partner has accepted. The first accepted partner starts a full 24-hour window if the Mac last checked in before they accepted. The service checks for a missed window every 30 seconds and when a fresh check-in arrives. The first detection queues one batch for the accepted partners in the same transaction that marks the window alerted. The sink publishes at a stable path so a delivery retry after interruption cannot publish a second batch. A new check-in rearms the monitor. Solo setups and pending invitations receive no mail.

Victor approved clean uninstall with the missed check-in alert as a fallback on 2026-11-21. Uninstall stops the daemon and its check-ins. **Leave Clearpath** gates the administrator prompt on an exact sentence and a 60-second monotonic countdown. The prompt runs a verified copy of the bundled service tool from a private stage, which remains usable after the installed service files are removed. The tool restores DNS through the shared service cleanup, verifies the exact system browser profile is gone, unregisters the app in the signed-in user's session and retires the verified Applications bundle as one operation.

When the installation has a configured pairing service, the authorized tool persists an uninstall event with an ID, timestamp and kind and removes the pairing configuration before restoring DNS. The event survives cleanup and retries in the root-only directory at `/private/var/db/io.clearpath.uninstall`. A restart during partial cleanup cannot resume authenticated check-ins. Delivery is tracked in #22. The solo trial creates no event.

### Community list refresh

The system job `io.clearpath.community-list` runs `clearpath-service refresh-community-list` when loaded and at the top of each hour. macOS coalesces missed calendar events into one run on wake. The command checks the last successful refresh on disk and downloads on the first run, after seven elapsed days, or after boot or wake if overdue. A failed check stays due. Uninstall removes the job and its state.

Clearpath downloads HaGeZi's curated NSFW domain list directly from the publisher's GitHub repository over HTTPS. It uses an anonymous request to one fixed URL with no browsing or policy data, credentials, cookies or redirects. The source publishes the list under GPLv3. Clearpath takes the list at runtime for local use and ships no copy of it. [HaGeZi NSFW domains](https://raw.githubusercontent.com/hagezi/dns-blocklists/main/wildcard/nsfw-onlydomains.txt) · [Publisher and attribution](https://github.com/hagezi/dns-blocklists#nsfw) · [GPLv3 license](https://github.com/hagezi/dns-blocklists/blob/main/LICENSE)

The download is staged in memory with a 4 MiB limit. The updater verifies the source version, declared entry count, unique domains and a range of 25,000 to 200,000 entries. It excludes Reddit, X, Tumblr and their associated domains, plus source rules that cover configured SafeSearch names or targets. The resulting list must still contain at least 25,000 entries. When replacing an installed list that meets that minimum, any refresh adding or removing more than 25 percent of its entries is rejected. Older versions and changed contents under the same version are also rejected. These checks bound the effect of a bad release. The source still determines which individual domains it classifies as adult.

The updater takes the existing service lock after downloading, rereads the installed policy and replaces only its adult list. Personal blocks, approved allow exceptions and SafeSearch mappings retain their existing precedence. The shared policy writer validates the whole staged policy and atomically replaces the installed file for the running filter to reload. Rejected downloads leave the last known good policy on disk. The service records `communityList.lastSuccess` and `communityList.sourceVersion` in `status` after promotion. An identical refresh records success without rewriting the policy. Missing metadata means the service has no confirmed refresh.

Costs accepted with the local DNS service, to be measured in the VM before Victor's Mac: VPN and split-DNS coexistence, network changes and sleep/wake, captive portals, and an administrator can change the DNS setting back (detected and alerted, not prevented). Bypasses listed in the assessment below (encrypted DNS to arbitrary endpoints, VPNs, proxies, Tor, Private Relay) still apply.

# Technical foundation assessment — 2026-11-17

The assessment that led to the V1 architecture. Its preference for the DNS proxy extension is superseded for V1 by the decision above.

## Decision and acceptance boundary

Use local domain policy, provider-supported SafeSearch DNS aliases, and explicit browser configuration. A **Swift `NEDNSProxyProvider` system extension** is the preferred next deployment experiment: it avoids replacing each network service's DNS settings and does not require owning a loopback port 53 or a full VPN tunnel. This is a conditional architecture decision, not a claim that the extension has been built or activated.

The demonstrated boundary is narrower: blocked domains cannot resolve **through this prototype**, configured search names resolve to forced-safe endpoints, and unrelated DNS can pass through. It preserves administrator access. It cannot prevent an administrator from removing protection, selecting another browser, changing policy, using a VM, or booting another OS. Reliable voluntary filtering is a plausible product; unavoidable protection under those freedoms is not a supportable promise.

## Options considered

| Mechanism | Useful capabilities | Material costs or gaps | Decision |
|---|---|---|---|
| `/etc/hosts` | Simple static names | No wildcard policy, weak updates, no CNAME, alternate resolvers/caches bypass; modifies global state | Reject as foundation |
| Local DNS daemon + system DNS replacement | Small, easy to demonstrate, all cooperative browsers | Requires privileged deployment, original resolver backup, VPN/split-DNS integration, sleep/network-change recovery; encrypted DNS bypass | Use high-port experiment only |
| Managed encrypted DNS profile / remote family DNS | Less local resolver code | Provider sees queries; custom policy often cloud controlled; standalone browser DoH may ignore it; profile installation/removal and local trust model need testing | Optional future mode, not privacy default |
| Native DNS Proxy | DNS flow interception without routing all IP traffic | Signing, entitlement, approval and lifecycle work; port-53 scope excludes arbitrary DoH/DoT/DoQ | Preferred next native spike |
| Native content filter | Allow/drop flows, app identity, hostnames where supplied | Cannot rewrite traffic; not a universal decrypted URL feed; missing host metadata, tunnels and shared IPs remain difficult | Optional later guard, evidence required |
| Packet tunnel or transparent TLS proxy | Broader traffic control | Routing conflicts, VPN coexistence, transport implementation burden; TLS interception requires a root certificate and harms trust | Reject for this scope |
| Browser policies / extensions alone | Google SafeSearch policy; browser URL rules and DoH controls | Browser specific; removable by admin; portable/new browsers outside coverage; Safari needs another layer | Supplement DNS |
| macOS 26+ URL Filter | System-operated WebKit/URLSession URL checks | PIR server and dataset tooling; other engines must participate voluntarily; does not rewrite SafeSearch | Not the minimum cross-browser solution |

Apple's [DNS proxy API](https://developer.apple.com/documentation/networkextension/nednsproxyprovider) describes transparent interception of UDP/TCP port 53 flows and exposes system DNS settings. This is why switching from one ordinary DNS server to another may be capturable by the native provider, whereas this isolated listener cannot capture it. Actual interception of explicit alternate resolvers remains untested.

[Deployment requirements](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment) permit macOS DNS proxies and content filters as system extensions from macOS 10.15. They run independently of the logged-in user. Direct distribution uses Developer ID signing. [Apple's entitlement setup](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.networking.networkextension) requires a capability-enabled provisioning profile. A free/open-source app can still incur developer signing/distribution costs. This experiment does not obtain signing, bypass SIP, install profiles, or request extension activation.

Apple [content filters](https://developer.apple.com/documentation/networkextension/content-filter-providers) separate the restrictive data-provider sandbox from a control provider that updates rules. This is useful for local privacy. Apple's [WWDC25 explanation](https://developer.apple.com/videos/play/wwdc2025/234/) describes allow/drop verdicts rather than traffic modification. Use DNS to enforce safe endpoints; do not assume a content filter can inject URL parameters. [`remoteHostname`](https://developer.apple.com/documentation/networkextension/nefiltersocketflow) is optional; [`url`](https://developer.apple.com/documentation/networkextension/nefilterflow/url) is documented only for WebKit-originated flows. Metadata coverage must be measured in each browser, not inferred from Safari or from SDK compilation.

The newer [URL Filter API](https://developer.apple.com/documentation/networkextension/url-filters) uses a local Bloom filter with PIR server lookups. Its automatic coverage is WebKit and URLSession; other networking engines must opt in. That server dependency and participation boundary make it a poor fit for this minimal local-first experiment.

## Proposed data path

```text
local domain files -> validate candidate -> atomic policy snapshot
                                           |
browser/system plain DNS -> native DNS Proxy -> local policy decision
                                           | block: NXDOMAIN
                                           | safe: resolve only provider safe target
                                           | allow: original network/scoped resolver
Chrome/Brave/Firefox policies -> prevent browser-managed DoH bypass
optional flow filter -> extra observable-host/domain/known-bypass checks
```

The prototype substitutes a loopback UDP/TCP server for the unimplemented native provider. Allowed requests go to one **explicit** upstream IP. It deliberately does not discover, overwrite, or claim to preserve the Mac's scoped DNS configuration. Before shipping, preserve VPN DNS, resolver search domains, captive portals, per-interface behavior and `.local`/mDNS. Do not resolve upstream targets using the OS resolver from inside intercepted DNS, which risks recursion.

## Policy and SafeSearch semantics

Decision order: explicit custom block; exact SafeSearch hostname; explicit allow exception; adult-list suffix block; otherwise forward. Exceptions intentionally bypass adult-list blocks; custom blocks always win. Allow rules overlapping a safe hostname are rejected. Matching uses label boundaries, lowercase ASCII/IDNA hostnames and a single optional trailing dot. IP literals, URL syntax, empty labels and oversized labels are not accepted as rules. Single-label and DNS-SD queries are forwarded. This prototype does not include a Public Suffix List; a rule such as `co.uk` can overblock and must be reviewed.

Use these provider-documented CNAME mappings, keeping the original HTTPS host and certificate verification:

| Provider | Example protected name | Forced endpoint | Scope |
|---|---|---|---|
| Google | `www.google.com` | `forcesafesearch.google.com` | Only configured Google search/country hostnames |
| Bing | `www.bing.com`, `edgeservices.bing.com` | `strict.bing.com` | Search and documented Edge sidebar endpoint |
| DuckDuckGo | `duckduckgo.com`, `www.duckduckgo.com` | `safe.duckduckgo.com` | Configured search hostnames |

Sources: [Google](https://support.google.com/websearch/answer/186669), [Microsoft](https://support.microsoft.com/en-us/bing/blocking-explicit-content-with-safesearch), [DuckDuckGo](https://duckduckgo.com/duckduckgo-help-pages/features/safe-search). The sample also maps Google/Bing apex names, `www.duckduckgo.com` and one Google regional name; those extras need browser validation. Do not rewrite all of `*.google.com`: that can break developer APIs, login and unrelated services. No universal rule covers every search engine. Unsupported engines require an explicit product decision to allow, block, or add verified provider support. YouTube Restricted Mode and content inside mixed-use sites are outside the implemented policy.

For A/AAAA, resolve the safe target through the explicit upstream and return CNAME plus its matching records. If it has no IPv6 record, return no unsafe IPv6 address. If resolution fails, return SERVFAIL, never ordinary search IPs. For protected hosts, suppress HTTPS/SVCB records to avoid alternate address hints. Rewrites do not assert the DNSSEC AD bit; synthesized policy answers cannot preserve authoritative DNSSEC signatures. The prototype trusts its upstream for allowed answers and performs **no independent DNSSEC validation**. Local DNS-rewriting compatibility with validating clients is unverified.

## Browser configuration

Inert samples are under `examples/`; they are not installed. Chrome's [`DnsOverHttpsMode`](https://chromium.googlesource.com/chromium/src/+/376fc41e87a058f7a7b300b0ec3a4982b4ec0960/components/policy/resources/templates/policy_definitions/Miscellaneous/DnsOverHttpsMode.yaml) supports `off`, and [`ForceGoogleSafeSearch`](https://raw.githubusercontent.com/chromium/chromium/main/components/policy/resources/templates/policy_definitions/Miscellaneous/ForceGoogleSafeSearch.yaml) forces Google SafeSearch. On macOS, an arbitrary JSON file in this repository is not a policy deployment: use a VM-only configuration profile/managed preference payload for `com.google.Chrome` and verify `chrome://policy`. A fresh Chrome user-data directory does not isolate machine policies.

Firefox's [policy documentation](https://mozilla.github.io/policy-templates/) supports `DNSOverHTTPS.Enabled=false` with `Locked=true`, plus `WebsiteFilter`. These settings do not supply universal SafeSearch; DNS still supplies the safe endpoints. Firefox supports `policies.json` in an app's distribution directory; a cloned unsigned/modified bundle may have signing implications. Use a disposable VM and verify `about:policies`, including private windows and later updates. Safari uses the controlled system path once the browser profile turns off its advanced tracking and fingerprinting protection (#61); Private Relay, VPNs and encrypted DNS profiles require separate validation. No Screen Time dependency is proposed.

## Privacy, lists and operational limits

All policy decisions stay local. No browsing/query log, analytics, account, URL history, TLS interception or root certificate is implemented. The upstream resolver still sees allowed DNS names and safe-target queries; the network can observe plaintext DNS. HTTPS endpoints see ordinary requests. Live smoke output deliberately records only fixed test domains. Local-only filtering does not mean queries never leave the device.

The tiny sample adult list proves matching, not classification quality. A production list pipeline needs versioned sources, license/attribution review, freshness health, size/change thresholds, staging, atomic promotion, last-known-good disk generations, and false-positive exceptions. HaGeZi is a candidate, but its repository carries [GPLv3](https://github.com/hagezi/dns-blocklists/blob/main/LICENSE); inspect dataset/source notices before redistribution. No third-party dataset is bundled here. The local importer validates syntax and rejects empty/corrupt input; it is not a supply-chain updater or crash-durable generation store.

The experiment bounds request workers at 32, returns truncation for UDP answers exceeding the client's clamped size, and supports one request per TCP connection. It has no cache, encrypted upstream, multi-resolver failover, mDNS routing, DNSSEC validator, DoH server, exhaustive DNS parser fuzzing or production load/security audit. Known CNAME block targets are checked; DNAME, unknown alias mechanisms and hardcoded IPs are not covered.

DNS caches, existing TCP/QUIC connections, service workers and offline content can outlive policy changes. A high-port resolver cannot revoke those connections. A flow filter may help with new observable connections, but that remains a hypothesis. Shared-host/path-specific adult material cannot be blocked precisely with domain policy. DoH to arbitrary HTTPS endpoints, DoT/DoQ, Private Relay, Tor, VPNs, remote browsers and proxies can bypass DNS-only filtering. Broad IP/443 or VPN blocklists would damage developer workflows without guaranteeing protection; do not ship them as the default.

## Next decision gate

Proceed to a signed DNS Proxy spike **in a disposable macOS VM**, with the same policy tests ported to Swift, only after accepting the cooperative threat model. Measure flow capture, original resolver routing, browser policy effectiveness, provider outage behavior and lifecycle recovery using the matrix in TESTING.md. Add a content filter only for a measured gap that it can actually close. If arbitrary encrypted DNS must be impossible while all admin/network tools remain unrestricted, revise that requirement before building the application.
